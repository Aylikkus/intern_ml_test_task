# Отчёт: постобработка OCR паспорта РФ

## 1. Итог

Файл `answers.jsonl` для test: принято 1058 из 2000 (52.9%; доля совпадает
с train: 52.7%), отклонено 942.

**Прогноз на test:** из 1058 принятых документов ожидается порядка 55 с
ошибкой (диапазон 40–75). Оценка: на train доля ошибочных среди принятых
= 81/1580 = 5.1%, правила отбора на test работают с той же интенсивностью
(доля отказов 47.1% против 46.9% на train).

Каскад «accept/reject» собран из трёх слоёв: детерминированные правила по
уверенности и формату, кросс-проверка визуальной зоны с MRZ и обучаемый
классификатор OCR-ошибок для текстовых полей. Для удобства используются
следующие обозначения:

- **C** — минимальная char_conf поля < 0.92;
- **M** — у поля нет предсказания;
- **Q** — glare > 0.15 или sharpness < 125;
- **F** — нарушение формата поля;
- **R1** — код подразделения не найден в справочнике.

Результаты на train (3000 документов, исходный evaluate.py):

| каскад | принято верно | с ошибкой |
|---|---:|---:|
| v1: правила (char_conf, формат, качество, справочник) | 1501 (50.0%) | 107 |
| v2: + MRZ-кросс-проверки + правдоподобие дат | 1501 (50.0%) | 92 |
| v3: + классификатор OCR-ошибок (T=0.5) | 1499 (50.0%) | 81 |
| v3: то же (T=0.7) | 1501 (50.0%) | 82 |

Отбор порога T и всех констант сделан по out-of-fold-оценкам классификатора
(5-кратная CV с группировкой по документам), итоговые ответы на train
прогонялись через evaluate.py. Выбран T=0.5: цена ошибочного отказа от
верного документа (~2 документа) несопоставима с выигрышем в «принят с
ошибкой» (−9..−11 относительно v2), т.к. такой документ обходится намного
дороже.

## 2. Разведочный анализ (первые эксперименты в experiments.ipynb)

Стартовая точка: точно совпадают с разметкой 52.9% документов (53.7% без
учёта регистра/пробелов); документов хотя бы с одной ошибкой — 1217,
ошибочных полей — 1838.

Характер ошибок (выравнивание SequenceMatcher): удаления 54%, замены 38%,
вставки 8%. Самые «страдающие» символы эталона: О (380), пробел (306),
С (245), А (236), Р (199), точка (185). Топ-пар «эталон → предсказание»:

- «О → ничего» 218
- «О → С» 143
- «А → Л» 102
- «С → О» 95
- «Р → В» 81

— типичные визуальные подмены OCR.

Уверенность символа плохо отделяет ошибку от верного символа:

- ошибочные символы: средняя conf 0.66, но p95 = 0.9995; 247 ошибочных
  символов имеют conf ≥ 0.99, 126 — ≥ 0.999, максимум 1.0000;
- верные символы: медиана 0.9995, p5 = 0.9862.

Перебор порога T («отбраковать документ, если есть символ с conf < T»):

- T=0.92 — ловит 80% ошибочных символов, задевает 0.8% верных; на уровне
  документов recall 77.7% при 4.2% ложных отбраковок;
- T=0.99 — recall 91.9%, но ложных отбраковок уже 73.3%.

Вывод: одной char_conf недостаточно — отсюда идея отдельного классификатора
ошибок (п. 3.2).

Связь качества снимка с ошибками (коэффициенты Пирсона с флагом
«документ ошибочен»): glare +0.37, sharpness −0.38, doc_px −0.38.
По корзинам glare: <0.05 — 33.5% ошибочных документов, 0.10–0.15 — 65.5%,
0.15–0.20 — 83.0%, 0.20+ — ~98%. По sharpness: <75 — 100%, 100–125 — 94.8%,
150–200 — 39.2%, 200+ — 30.0%. По разрешению: <700 px — 95.7%,
700–1000 — 97.0%, 1000–1500 — 73.3%, 1500–2500 — 34.7%.
Источник снимка влияет слабо: web 46.2%, mobile 42.6%, mobile_v2 45.5%
ошибочных документов. Отсюда пороги правила Q: glare > 0.15 или
sharpness < 125.

Каскад v1 (только правила) на train: recall 91.9% (1213 из 1320 ошибочных),
ложные отбраковки 10.7% (179 из 1680 верных), «принят с ошибкой» 107 (3.57%).
Вклад правил: C — 1114 документов (из них ошибочны 1043), M — 332/263,
Q — 365/328, F — 162/162, R1 — 107/78. Нарушения формата по полям:
даты рождения/выдачи 58 и 61, пол 20, номер бланка 20, ФИО 4.

## 3. Метод

### 3.1. MRZ-кросс-проверка (главная находка)

MRZ заполнена у 94% документов, но в каскаде не использовалась. Формат
восстановлен по данным:

```text
строка 2: [0:9) номер = серия[:3]+номер бланка, [9] контрольная цифра (CD),
          [13:19) дата рождения ГГММДД, [19] CD, [20] пол,
          [29:35) дата выдачи, [35:41) код подразделения,
          [42] CD персонального поля, [43] составная CD.
```

Контрольные цифры ICAO (7-3-1) сходятся на train в 99.6/99.7/97.9/95.3%
случаев — это бесплатная проверка целостности самого MRZ. Пол в MRZ
совпадает с разметкой в 100%, даты и номер — в ~99.5%.
Транслитерация нестандартная (leetspeak): А-A … Ч-3, Ш-4, Э-6, Ю-7, Ь-9,
Я-8, Й-Q, Ж-J, Щ-W; таблица выведена выравниванием MRZ с разметкой.

Правила (расхождение виз. зоны и MRZ = ошибка в одном из двух):

| правило | что проверяет | поймано / ложных |
|---|---|---:|
| X1 | дата рождения не совпала | 43 / 0 |
| X3 | номер бланка не совпал (MRZ цел) | 56 / 0 |
| X4 | дата выдачи или код не совпали | 69 / 1 |
| V1..V3 | правдоподобие дат (выдача после 01.10.2026, возраст при выдаче < 14, выдача раньше рождения) | 33 / 0 — ловят испорченные даты |

Правила X3/X4 применяются только при целом MRZ (`cd_fail_count == 0`):
испорченный MRZ не должен отбраковывать правильную визуальную зону.

### 3.2. Классификатор OCR-ошибок

Задача: по значению одного текстового поля (3×ФИО, Birth_place_ru,
Issue_organization_ru) предсказать вероятность того, что значение содержит
ошибку. Разметка бесплатная — сравнение предсказания с GT на train.
Признаки: форма char_conf (min/mean, доли ниже порогов), правдоподобность
формата, символьная триграммная LM, обученная на GT того же поля (доля
OOV-триграмм ловит «СМИРНОВ→СМИРНСВ» даже при char_conf 1.0), MRZ-признаки
документа, качество снимка. Модель — HistGradientBoosting (scikit-learn).
OOF AUC 0.977 (по полям 0.93–0.99). Правило S: отказ, если p > 0.5 хотя бы
у одного текстового поля.

Модель обучается отдельным скриптом `train_model.py` и хранится вместе с
признаковым окружением (триграммные LM) в `model/ocr_error_classifier.pkl`
(~0.5 МБ); `postprocess.py` только загружает её — train-данные для запуска
постобработки не нужны.

## 4. Что выяснил (важное)

- Ошибки виз. зоны и MRZ **частично коррелированы**: у 28% документов
  с ошибкой в ФИО MRZ показывает то же искажённое имя (видимо, один и тот же
  испорченный текст отрисован в обеих зонах). Поэтому MRZ — не истина
  в последней инстанции: используем только факт **расхождения**, и часть
  ошибок (в среднем ~80 документов train) для этого метода непрозрачна
  в принципе.
- Согласие MRZ **не** доказывает правильность поля: попытка «одобрять
  документы, отбракованные по low-conf, если MRZ всё подтверждает» дала
  517 принятых с ошибкой — MRZ не видит поля Birth_place_ru и
  Issue_organization_ru, где сидит большинство ошибок.
- Утечки в обучении классификатора давали фантастические, но фейковые
  метрики: AUC 0.9998 при обучении на полном train (лексикон и LM содержали
  GT самого документа). Честные протоколы: для CV — корпус/LM только по
  обучающим фолдам; для продакшн-модели — leave-one-doc-out (триграммы
  своего документа вычитаются из корпуса).
- Признак «близость к словарю train» отравлен сдвигом распределения:
  на train медиана сходства 1.0 (своё GT в словаре), на test 0.67 (имена
  не встречались) — с этим признаком классификатор отклонял 1092 из 1096
  чистых документов test. Признак удалён; test систематически «грязнее»
  train (5-й перцентиль min char_conf 0.29 против ~0.99), это надо было
  учесть отдельно.
- Серия «пол» и «CD флаги» как самостоятельные правила бесполезны (0 и 19
  ложных срабатываний соответственно).

## 5. Что не сработало / ограничения

- Override старых правил согласием MRZ (см. выше) — отклонено.
- Лексиконные признаки — отклонены (сдвиг распределения).
- Не реализована проверка «настоящей» действительности паспорта (замена
  в 20/45 лет): по строгой трактовке до 22% документов train были бы
  «просрочены»; выбрана консервативная трактовка (невозможные даты).
- Автоисправление (коррекция ошибочных полей) не делалось: без надёжной
  локализации ошибки и уникального кандидата correction превращается
  в «принят с ошибкой».
- Остаточные 81 ошибочных приёма на train — в основном поля, где MRZ
  бессилен (Birth_place, Issue_org) плюс коррелированный шум в ФИО.

## 6. Как запустить

```bash
python experiments/train_model.py   # обучение классификатора
python postprocess.py data/test_predictions.jsonl answers.jsonl
```

Структура репозитория: `postprocess.py`, `answers.jsonl` и `README.md` —
в корне; библиотеки `mrzlib.py` и `errfeatures.py` — в `lib/`; обучение
модели, `evaluate.py` и ноутбук с экспериментами — в `experiments/`;
обученная модель — `model/ocr_error_classifier.pkl`; данные — `data/`
(`train_predictions.jsonl`, `train_labels.jsonl`, `test_predictions.jsonl`),
справочник — `reference/subdivisions.csv`. `postprocess.py` читает только
test-данные, справочник и pickle модели — train-данные ему не нужны.
Если рядом со входным файлом есть свой `reference/`, подойдёт и он.

Все зависимости — в `requirements.txt` (`pip install -r requirements.txt`).
Работает на CPU, без интернета.

Эксперименты и все числа — в `experiments/experiments.ipynb`: разведка
(fail-analysis, quality-correlation, char-conf-threshold, cascade), MRZ
(mrz-*), классификатор (ocr-*, cascade-ml-*).
